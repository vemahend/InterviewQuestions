# Question ID: Q-ba031f0803e73810

### Real-world scenario

A downstream service fails repeatedly and retries overload the entire platform.

### Step-by-step explanation

1. A timeout bounds each attempt. A retry handles transient failures using exponential backoff and random jitter.

2. A circuit breaker opens after repeated failures and fails fast. After a recovery interval, limited half-open probes determine whether to close it.

3. A bulkhead limits concurrent calls to isolate a failing dependency.

4. Use IHttpClientFactory and a resilience pipeline with an overall deadline. Retry only safe or idempotent operations.

### Execution flow

```text
Closed → failures → Open → Half-open → Closed or Open
```

### Common mistakes and best practices

Retries are not durability. Use a durable queue for work that must survive an outage.

### Interview-ready answer

Set a per-attempt timeout and overall deadline. Retry only transient failures and safe or idempotent operations with exponential backoff and jitter. Open a circuit after repeated failures, then allow limited half-open probes. Isolate dependencies with concurrency limits. Monitor failures and avoid retry storms.
