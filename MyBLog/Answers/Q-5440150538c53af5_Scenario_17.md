# Question ID: Q-5440150538c53af5

### Real-world scenario

A payment controller accepts requests, writes to a database and calls a provider without safeguards.

### Step-by-step explanation

1. Require authentication and resource-level authorization. Validate amount, currency and input; derive sensitive values server-side.

2. Move orchestration to an application service. Enforce idempotency and use a local transaction for related database writes.

3. Use an outbox for external work, structured logs without secrets and centralized exception handling.

4. Test invalid input, unauthorized access, duplicate requests, provider timeout and rollback.

### Execution flow

```text
Controller → authorization/validation → service → DB + outbox → provider
```

### Common mistakes and best practices

Authentication alone does not authorize access to another customer's account.

### Interview-ready answer

Require authentication and resource-level authorization, validate request data, use structured logging without sensitive details, and centralize exception handling. Keep business logic in a service, use an atomic transaction for related database writes, and enforce payment idempotency. Use an outbox for external events and add failure and concurrency tests.
