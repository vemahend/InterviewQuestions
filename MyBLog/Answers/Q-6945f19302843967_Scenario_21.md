# Question ID: Q-6945f19302843967

### Real-world scenario

A singleton background worker captures a scoped DbContext.

### Step-by-step explanation

1. Singleton lives for the service provider; scoped lives for one scope, typically a request; transient is created on resolution.

2. A captured scoped context can retain stale tracked data and be used concurrently or beyond its intended lifetime.

3. Inject IServiceScopeFactory and create a scope per unit of work; resolve and dispose the context inside it.

4. Alternatively use IDbContextFactory. Enable scope validation and use separate contexts for concurrent work.

### Execution flow

```text
Singleton → create scope → scoped DbContext → work → dispose
```

### Practical example

```csharp
await using var scope = scopeFactory.CreateAsyncScope();
var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
await ProcessBatchAsync(db, ct);
```

### Common mistakes and best practices

Making DbContext singleton is not a fix.

### Interview-ready answer

A singleton must not capture a scoped DbContext because it can outlive the request and is not thread-safe. For a background singleton, create and dispose a scope per unit of work using IServiceScopeFactory, then resolve the scoped service inside that scope.
